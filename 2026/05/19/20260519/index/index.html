赛博聊天室 2.0——从能聊天到相对好用

提示：此文章为本人实践后由AI总结生成，可能存在错误，请谨慎参考。

上一篇 赛博聊天室 1.0 讲的是从零搭建微服务骨架，让 6 个 AI 角色能通过 curl 命令聊天。这篇讲 2.0 版本怎么把一个”能跑的 Demo”改造成一个”真正能用的系统”。

一、1.0 → 2.0 变更全景

二、新增技术栈

新增项 技术 用途
实时通信 Spring WebSocket 替代 HTTP 轮询，实时推送 AI 回复
流式响应 SSE (SseEmitter) 可选的流式输出通道
数据库 MySQL 8 + JPA/Hibernate 持久化对话、消息、Skill、文件记录
文档生成 Apache POI + iTextPDF AI 生成 Excel/Word/PDF 报表
登录 Vue Router + 前端路由守卫 多用户隔离基础
工作流 可视化拖拽 + 拓扑排序 多 Agent 串联执行编排

三、核心功能演进——新增篇

3.1 WebSocket 实时通信

1.0 的痛点：前端发 HTTP POST，然后轮询等待 AI 回复。网络延迟高时体验很差，而且无法实时看到 Agent 之间的协作过程。

2.0 方案：引入 Spring WebSocket，前端建立长连接，后端实时推送事件流。

关键实现（ChatWebSocketHandler，WebSocket 消息处理器）：

  • 每个消息以 JSON frame 格式推送：{event, data}
  • 事件类型：start → tool（工具调用）→ chat（回复）→ done → error
  • CrossAgentTool 的回调通过 WebSocketSession 实时推送给前端，实现 Agent 协作过程的可视化
  • ping/pong 心跳机制防止连接超时

试错记录：

  • 最初用 HTTP SSE (SseEmitter)，但 SSE 是单向的，前端还需要额外发 POST 请求获取回复，状态管理复杂
  • 改用 WebSocket 后，一个连接搞定双向通信，但要注意 @CrossOrigin 和 setAllowedOrigins("*") 的配置
  • CrossAgentTool 的 ThreadLocal 回调在异步 CompletableFuture.runAsync 中丢失，改用显式 setCallback 传递

3.2 MySQL 持久化 + 数据同步

1.0 的痛点：对话历史存在 localStorage，刷新页面、换浏览器、清除缓存就全没了。

2.0 方案：5 张表覆盖所有数据持久化需求。

云端同步机制（DataController，对话/消息 CRUD 接口）：

  • 前端每次操作对话/消息时，同步写入服务端
  • 服务端提供 GET/POST/DELETE 完整 CRUD API
  • 并发安全：per-conversation 锁 + MySQL 死锁自动重试
  • 顶部导航栏的 ☁ 按钮控制同步开关

试错记录：

  • 最初用 localStorage 做对话历史，本地没问题，但多人协作时数据不同步
  • 迁移到 MySQL 后遇到并发死锁问题（多个请求同时写同一对话的消息），用 ConcurrentHashMap<String, Object> 做 per-conversation 锁解决
  • JPA ddl-auto: update 在生产环境不安全，但个人项目够用

3.3 Skill 动态 Agent 体系

1.0 的痛点：每个 Agent 都是写死的 @AiService 接口，想加新角色必须改代码、重新编译。

2.0 方案：引入 Skill 概念 + 动态注册机制，运行时就能创建新 Agent。

三阶段加载机制：

阶段 触发 来源 说明
1 启动 @PostConstruct skills/ 目录 从文件加载新 Skill 到 DB
2 启动 @PostConstruct DB 查询 恢复已启用的 Skill 对应的动态 Agent
3 运行时 API /api/skill/generate AI 生成新 Skill，实时注册

关键实现（DynamicAgentService，动态 Agent 核心服务，绕过 @AiService 直接调用 ChatModel）：

试错记录：

  • 最初所有 Agent 都用 @AiService 注解 + wiringMode = EXPLICIT，每个 Agent 都要写一个 Java 接口
  • 想加新角色时发现必须改 Java 代码 → 重新编译 → 重启服务，迭代效率极低
  • 改为 DynamicAgentService 直接调用 ChatModel，通过 ChatRequest 手动构建请求
  • 遇到 @Tool 方法找不到的问题：@AiService 自动注册工具，但手动模式需要自己实现 ToolProvider
  • 最终设计了 SmartToolProvider（见 3.5），实现了按需工具注入

3.4 Agent 协作：CrossAgentTool

新增能力：Agent 之间可以互相调用。芬妮在回答时可以”请卡芙卡帮忙”。

安全机制：

机制 实现 目的
深度限制 MAX_DEPTH = 2 防止 Agent 互相调用导致无限递归
工作流隔离 WORKFLOW_MODE ThreadLocal 工作流执行中禁止交叉调用
事件追踪 ToolCallEvent + 回调 每次调用记录 from → to，推送到前端可视化

前端可视化：当芬妮调用卡芙卡时，聊天区会实时显示一条事件卡片：

试错记录：

  • CrossAgentTool 的 @Tool 方法通过 @Autowired ApplicationContext 获取其他 Agent 的 Bean，循环依赖风险
  • 用 getBean() 延迟获取解决：每次调用时才查 Bean，而非构造时注入
  • 最初 6 个 @Tool 方法全部注册给所有 Agent，浪费 token → 改为 SmartToolProvider 按需注入（见 3.5）

试错记录：

  • 最初用 tools = {"dateTool", "emailTool", "calculatorTool", "fileTool", "weatherTool"} 全量注册
  • 发现 token 消耗严重：每个工具的描述约占 100-200 token，5 个工具 + 6 个 CrossAgent 方法 ≈ 1500 token
  • 第一版 SmartToolProvider 用简单正则匹配，误判率高 → 后来改为按工具名 + 描述双关键词匹配
  • CrossAgentTool 的缓存 key 最初用类名，后来改为 beanClass#toolName 避免不同 bean 的同名方法冲突

3.6 DocumentTool：AI 生成报表

新增能力：AI 可以直接生成 Excel、Word、PDF 文件。

文件中心（FileCenterController，文件下载/删除/统计）：

  • GET /ai-agent/files/all — 查询所有导出文件
  • GET /ai-agent/files/{id}/download — 下载文件（Content-Disposition + UTF-8 编码文件名）
  • DELETE /ai-agent/files/{id} — 硬删除（磁盘 + 数据库）

试错记录：

  • Apache POI 的 XSSFWorkbook 在生成大表格时内存溢出 → 限制最大行数 + 流式写入
  • 文件名中文乱码 → 用 URLEncoder.encode(fileName, StandardCharsets.UTF_8) 处理
  • DocumentTool 需要知道当前是哪个 Agent 在调用（用于确定导出目录），通过 ThreadLocal<String> 从 Controller 传递

3.7 工作流编排

新增能力：可视化拖拽创建多 Agent 工作流，每个节点是一个 Agent，带自定义指令。

后端执行（WorkflowController，工作流 CRUD + 编排执行）：

  1. 找起始节点（没有入边的节点）
  2. BFS 拓扑排序，按层级依次执行
  3. 每个节点的输出作为下一个节点的输入上下文
  4. CrossAgentTool.setWorkflowMode(true) 禁止节点间交叉调用

前端编辑器（WorkflowEditor.vue，可视化拖拽 + SVG 连线）：

  • 拖拽节点定位
  • 从输出端口拖到输入端口连线
  • 每个节点可自定义指令（作为系统提示词注入）
  • SVG 绘制连线 + 箭头

3.9 多模态：图片识别

新增能力：用户可以上传图片，AI 能识别图片内容。

试错记录：

  • 需要模型支持视觉能力（如 DeepSeek-VL、GPT-4V），普通文本模型会报错
  • data:image/png;base64,... 的 MIME 类型需要根据图片实际格式判断
  • 大图片 base64 编码后体积膨胀 33%，设了 5MB 上传限制

3.10 登录系统 + Vue Router

1.0 的痛点：打开页面直接进聊天室，没有用户概念。

2.0 方案（LoginPage.vue，登录页 + Vue Router 路由守卫）：

  • 登录页：随机背景图 + 随机角色头像 Logo
  • sessionStorage 存储登录状态
  • router.beforeEach 路由守卫拦截未登录访问
  • 用户名决定数据隔离（userId 字段区分不同用户的对话）

四、架构优化——踩坑篇

4.1 从 @AiService 到 DynamicAgentService

这是 2.0 最大的架构变更。

1.0 的 @AiService 模式：

优点：声明式，代码简洁。
缺点：工具列表编译时固定，无法运行时动态增减；加新角色必须写新接口。

2.0 的 DynamicAgentService 模式：

优点：完全动态，运行时可增减 Agent 和工具。
缺点：代码量增加，需要自己实现 tool call 循环。

为什么保留了 @AiService：6 个内置 Agent 仍用 @AiService（因为 BuiltInSkillInitializer 启动时会同时注册到 DynamicAgentRegistry），新增的 Skill 角色用 DynamicAgentService。两者共存，通过 AiChatService 接口统一调用。

问题：DynamicAgentService 的 systemPrompt 是在注册时确定的，但有时需要在请求级别追加额外指令（如工具绑定、自定义系统提示）。

八、总结

2.0 版本的核心思路是把 Demo 变成系统：

  • 数据不丢：MySQL 持久化 + 云端同步
  • 体验不卡：WebSocket 实时推送
  • 扩展不改代码：Skill 动态注册 + SmartToolProvider 按需注入
  • 协作可视化：CrossAgentTool + ToolCallEvent 实时展示 Agent 之间的对话
  • 产出可交付：DocumentTool 生成报表 + 文件中心管理
